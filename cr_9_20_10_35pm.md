### Serving and adapter lifecycle

`serving.py`, `tpu/vllm_tpu_server.py`, `config.py`, `commands.py`, and the farm
profiles extend the existing executor and engine startup path. A v4-32 farm uses
four TP4 engines, one on every host; there is no trainer on that slice. The head
Ray Serve gateway listens on **24800**, and each engine listens on **24801**.
The gateway is a private network endpoint, not public authenticated serving or
stable DNS. Engine addresses remain internal to the farm.

The farm accepts a streamed PEFT archive through
`POST /skyrl/v1/upload_lora_adapter`. The sender does not need a pathname shared
with the remote TPU. Upload drains generation, distributes the archive, and
commits a version only after every engine acknowledges the expected hash.
`previous_lora_name` supports replacement at the one-adapter capacity limit.
Native token IDs, sampled logprobs, masks and thinking metadata pass through the
existing client path. `/v1/models` is still a names API; it is not hash attestation.

Lease endpoints are `/acquire_lease`, `/release_lease`, and `/status`. Generation,
tokenization and uploads carry the lease identity. Status distinguishes ownership,
uploading, readiness, expiration and quarantine, and reports expected/ready engine
counts and the adapter SHA-256. The hash describes the exact archive bytes, not a
fresh numerical fingerprint of in-memory tensors. A successor cannot use its
predecessor's adapter without its own publication/verification.

Prefix caching is off on the v4 farm profiles. The prior Qwen cached greedy probe
diverged, including base-model requests; fresh-cache repetitions matched. This
motivated the restriction but does not establish the root cause of every observed
concurrent multi-adapter discrepancy. Model-download and JAX compilation caches
remain enabled. Local v6e profiles retain their existing prefix-cache setting.

### Borrowing and scheduling

- `borrowing.py`: lease acquisition, renewal, bounded preparation, attestation,
  remote generation, expiry/health handling, draining and local fallback.
- `borrowing_phase.py`, `tpu/run_ttd_ensemble.py`, science bootstrap hooks:
  connect sampling phases to the borrower while preserving the native payload.
- `run_borrowing.py`: ownership lasts across sampling, optimizer work and
  checkpoints. Finishing a sampling phase drains generation but retains the farm.
- `hybrid_scheduler.py`: one queue of whole generation groups, bounded local and
  remote dispatch, completion-rate estimates, and a local retry when a remote
  result cannot be used. It does not split a group across adapters or change
  the advantage computation.
- `hybrid_benchmark.py`: paired local-only/hybrid measurements, native-response
  checks and raw answer capture. The tool exists; the required production
  speedup result has not been established.

AC2 has four local inference engines plus up to four remote engines. RG-LRU has
three local engines, with the other local inference-side host used as a TPU
grader. Each HTTP generation request remains whole. The scheduler permits four
remote groups concurrently; engine `max_sequences=16` is a distinct setting from
HTTP `n` and the total 32-rollout training group.

Initial remote publication can run asynchronously while local requests proceed.
A new adapter alias contains the lease identity and archive digest. Remote
routing opens only after publication and compatibility checks succeed. Failed
remote responses cannot enter the learner batch; code retries the same payload
locally. This preserves request parameters, not necessarily identical sampled
text. Disconnected remote work may still execute; its result must not be returned
as a second learner input. Real TPU failure-injection validation remains pending.

Defaults in this campaign are a 300-second lease, 30-second renewal, 90-second
health grace and 120-second abandoned-work drain/quarantine limit. A local engine
failure remains fatal under these profiles. An ingress restart invalidates its
leases; clients must reacquire and republish. An ambiguous acquire can deliberately
prevent another claim rather than risk owning two farms; reviewers should check
that conservative failure path and its recovery/liveness implications.

### Compatibility checks

`serving_identity.py` compares model revision, model/tokenizer metadata, serving
wrapper source hashes, installed package versions, Python source hashes and
available package provenance. The implementation now recognizes `vllm-tpu` as
well as `vllm`. The resulting contract hash must match for an attested assignment
and claim. This is stronger than comparing a model alias, but it does not prove
numerical equivalence, identical compiled binaries, or full legacy environment
identity. Hardware-specific cache flags are intentionally excluded.

### Dynamic farm management

The **user-systemd** service `skyrl-hybrid-farm-discovery.service` runs on the
login/controller host, from a frozen copy of the reviewed discovery/admission
modules. It is not a daemon independently installed on every TPU host. Its
configured pools are:

- Farms: `tpuswarm-v4-32-central2-smoke`.
- Training: `tpuswarm-v6e32-east5b-qwen35` and `tpuswarm-v6e32-central1b`.
- **v4-64 is not currently included.**

Each pass reads the SkyPilot queue, probes running farms through existing SSH
access, checks all four replicas, and reads the farm head's private IP from GCP
metadata. It discovers opted-in training jobs by pool, not a fixed job-ID list.
It reads each job head's descriptor and posts a replacement URL list to
`/skyrl/v1/borrowing/services`. Updates include model, run ID and ingress instance
identity so a stale update is rejected after a restart. The loop sleeps 30 seconds
after a pass; network probes add latency. The singleton lock and systemd restart
policy prevent competing local instances and recover the discovery process.

There is **one updated gateway per training job**, not a separately maintained
farm list on every trainer rank. Actual generation and adapter traffic travels
directly from that gateway to the farm's private IP:24800; SSH is for discovery
control requests, not a tunnel carrying rollouts.

Discovery assignments are advisory; the farm's atomic lease is authoritative.
An existing healthy lease survives removal of its URL from the candidate list.
An inventory failure preserves the previous list; an individually unhealthy farm
can disappear from the next candidate list. Borrower health/lease checks remain
responsible for safely admitting requests. A replacement farm is acquired during
admission or a later sampling phase, not by moving an in-flight generation.

`farm_admission.py` preserves existing owners and gives AC2 precedence. Spare
same-model capacity may serve RG-LRU after matching AC2 has a reservation.
**Current qubit admission is stricter:** while any AC2 remains outstanding, the
code blocks a new qubit reservation, even if a different model's farm is free.
This differs from the recently discussed per-model spare-capacity policy and
needs review before v4-64 borrowing is enabled. Existing owners are not preempted.

### Campaign, topology, recovery and packaging

The current campaign uses **10 total steps**, including restored progress:
`NUM_EPOCHS=10`, with the client iterating `range(start_batch, cfg.num_epochs)`.
For example, Qwen RG-LRU resumes at 5 and has five more updates, not ten more.
The recipe retains 16 groups × 32 rollouts, importance-sampling loss, mean-baseline
advantages, seed 1, native thinking, 22,528 context and a 16,384 phase-one budget.
This is single-policy training; the earlier multi-policy research discussion is
not the deployed experiment design. AC2 and Gemma RG-LRU currently require an
initial farm reservation before starting trainers. Qwen RG-LRU explicitly does
not. Thus, even after fixing Gemma RG-LRU bootstrap reuse, it can wait for farm
capacity; five assigned east workers does not imply five actively training jobs.

The build/config changes also allow the narrowly specified v5p-64 CPU circuit
placement topology: one trainer plus seven TP4 inference engines. Science host
setup validates that shape and uses the existing `ibm17-proxy-v1` grader path.
Initial parent pools, canonical run IDs and cloud checkpoint roots are preserved
where resuming. Different trials' trees and optimizer states are not merged.
Run names containing an old hardware label are not reliable placement evidence.

Deployment scripts validate profiles, checksum immutable bundles and uploads,
record launch intent, prevent duplicate active canonical runs, and preserve
recovery metadata before replacing jobs. Cloud DB integrity and completed
checkpoint registrations were checked for the selected resumes. The fifth east
run has a separate verified step-5 preflight. Model/HF and Orbax prefixes remain
shared read sources; new compile writeback prefixes are isolated and seeded from
existing caches. The runtime retains the GCS/tmpfs cache implementation from the
base executor, including generation/checksum validation.

Durable paths are recorded per job in `prepared.json` and `preflight.json` under
[tpu/science/results/reallocation-10step-20260921](tpu/science/results/reallocation-10step-20260921).
Typical cloud paths are `gs://<bucket>/ray-training/<run>/client/tinker_log/<run>/`,
`.../checkpoints/` and `.../tinker-backup.db`. Recovery metadata snapshots live in
`migration-snapshots/reallocation-10step-20260921/` or the fifth-run snapshot prefix.
On TPU hosts the run root is `~/.cache/<run>/`; caches are under `ram/`, logs and
client state under `runs/<run>/`, and immutable code under
`~/.cache/skyrl-ray-code/<archive-sha256>/`. Local build archives live under the
ignored `.science/reallocation-10step/packages/` directory.

   config with the current config. The changed deployment is rejected with
   `bootstrap config changed; use a new run ID`. Its existing 29-parent pool was
   verified, but the deployment left bootstrap enabled. Review explicit reuse of
   the completed pool with bootstrap disabled; do not bypass the contract or
   regenerate silently. Repeated Sky recovery does not fix this mismatch.
2. **Gemma circuit:** attempts 1–2 lacked the pinned Python 3.12.12 because old
   uv did not recognize it. All eight hosts were repaired with an isolated newer
   uv installer, preserving runtime locks. Attempt 3 failed trainer compile-cache
   restore. A separate validated restore reused 177 files and fetched 62; attempt
   4 then failed restore on inference host rank 3. The underlying transfer exit
   remains unexplained. The managed queue exhausted its bounded retry and is
   blocked; an active queue daemon does not mean active circuit training.
3. **Muse farm:** it admitted the AC2 run, then its controller recorded
   `local inference fatal: RuntimeError: local inference failed` at 02:32:29 UTC
   and returned to PENDING in the review inventory. The underlying engine cause
   still needs investigation. Discovery removed it from Muse AC2's candidate
   list. See the attached supplemental failure/discovery records; active local
   requests do not establish a fully validated farm-loss recovery.
4. **Prior resume helper failure:** old Gemma AC2/Qwen RG-LRU attempts lacked
   `pool_step_for_resume`. The current source overlay includes that helper;
   current-attempt reload still needs runtime acceptance. Logs append under

5. **Disk preparation:** the standalone head initially had 28 GiB free, below

## v4-64 borrowing: agreed direction, not enabled

The user agreed it is sensible to allow v4-64 qubit jobs to use spare farms,
while retaining local inference and AC2 → RG-LRU → qubit priority. This review
checkpoint precedes that rollout:

- All three deployed v4-64 profiles have borrowing disabled.
- Discovery watches only the two v6e training pools.
- Adding the v4-64 pool to systemd alone is insufficient: the profiles must opt in
  to updates, run leases, attestation and scheduling.
- Initial farm admission should be optional so qubit runs do not hold allocated
  TPUs idle while AC2 owns the farms.
- Review the global-AC2 block described above before promising per-model spare
  borrowing. Preserve current owners and do not preempt an active AC2 lease.
- Rebuild/check/upload immutable profiles and safely resume existing runs rather
  than assuming a local JSON edit changes their deployed configuration.
